# 사주담 — 3대 고전 통합 해석 프롬프트 통합 스펙 (2026-08-10)

노이반이 제공한 "전통 명리학(사주) 통합 해석 프롬프트" 전문을 사주담(saju-wellness)
기본 이론에 추가·개선하기 위한 구현 스펙이다. 기존 캐주얼 일일운세 흐름(daily-energy,
운세요약/오행분석/에너지인사이트/오늘의조언/별자리메시지)은 그대로 유지하고,
이 스펙은 그 위에 "정밀 사주 풀이(DEEP READING)" 기능을 신규 추가하는 것이다.

## 출처
사용자 제공 프롬프트 전문 (출처 명시 필수): 노이반 작성 "전통 명리학(사주) 통합 해석
프롬프트" — 자평진전/적천수/궁통보감 3대 고전 기반, 만세력 입력 강제, 신살 보조화,
QUICK/STANDARD/DEEP 3단계, 10단계 해석 구조. 세션 날짜: 2026-08-10.

## 핵심 설계 원칙 (반드시 코드에 반영)

1. **3대 고전 관점 분리 후 병기**
   - 《자평진전》(격국·사회적 성패)
   - 《적천수》(강약·내면 심리)
   - 《궁통보감》(조후·계절적 편안함)
   - 세 관점 결론이 갈리면 숨기지 않고 [자평진전 관점]/[적천수 관점]/[궁통보감 관점]/
     [충돌 지점]/[최종 종합 판단] 형식으로 병기한다.

2. **만세력 입력 강제**
   - 생년월일시만으로 절기·대운·세운·신살을 LLM이 임의 계산하지 않는다.
   - 사주팔자(년/월/일/시주)는 이미 서버(saju_engine.py, 검증된 lunar-python 기반)가
     계산한 값만 사용한다. 이는 기존 구조와 일치 — 그대로 활용.
   - 대운은 get_daewoon()으로 계산된 값만 사용.
   - 세운(연도별 간지)은 신규 계산 함수 필요 (아래 "필요 신규 계산" 참조).
   - 신살/귀문/십이운성은 신규 계산 함수 필요.
   - 계산기 결과가 없는 항목은 "판독 불가 / 분석 제한 / 추가 입력 필요"로 명시하고
     LLM이 임의로 채우지 않도록 프롬프트에 강제한다.

3. **신살은 보조 지표로 격하**
   - 격국·용신·조후보다 우선하지 않는다.
   - 신살 하나만으로 사고/질병/이별/성공을 단정하지 않는다.
   - "반드시", "무조건", "100%", "운명적으로" 표현 금지.

4. **QUICK / STANDARD / DEEP 출력 모드**
   - QUICK: 1,2,6,7,8(축약),9,10단계만. 대운/세운 상세 표 생략.
   - STANDARD: 1~10단계 전체 + 평생대운표 + 향후 5년 세운표.
   - DEEP: 1~10단계 전체 상세 + 평생대운 전체 + 과거 구조적 전환구간 + 향후 20년 세운표
     + 고전 간 충돌 분석 + 용신 3분리 종합판단.

5. **10단계 구조**
   1단계 사주 구성 총평 / 2단계 기본 성격·성향 / 3단계 대운 흐름 / 4단계 세운 흐름 /
   5단계 신살·귀문·십이운성(보조) / 6단계 직설 단점·보완법 / 7단계 직설 강점·성장가능성 /
   8단계 분야별 종합(재물/건강/연애/가족/학업/직업/이동/성공) / 9단계 현재~향후 3년
   결정지도 / 10단계 최종 요약+반증조건+분석한계.

6. **안전장치 (기존 saju-wellness 법적 포지셔닝과 정합)**
   - 첫 줄 고정 [해석 안내] 문구 필수 — "검증된 예측·의학적 진단·법률·투자 조언이 아닙니다."
   - 사망/중병/사고/파산/범죄/이혼 등 확정적 예언 금지 — 기존 disclaimer 원칙과 일치.
   - 마지막 줄 고정 문구 필수.
   - 이 원칙은 saju-wellness 기존 법적 문구("문화·오락 서비스", "심리상담 대체 아님")와
     완전히 호환되므로 병렬로 유지.

## 기존 코드베이스와의 통합 지점

- `saju_engine.py`: get_saju(), get_daewoon() 그대로 재사용. 세운·신살·십이운성 계산
  함수가 없으므로 신규 추가 필요:
  - `get_sewoon(start_year: int, count: int) -> list[dict]`: 연도별 세운 간지 계산
    (calc_year_pillar 로직 재사용 가능 — year_pillar 계산과 동일한 60갑자 순환).
  - `get_sinsal(eight_char: dict) -> dict`: 도화/역마/천을귀인/문창귀인/괴강/백호/양인/
    화개/홍염 중 최소 3~5종 우선 구현 (전통 계산 규칙 기반, 일지 또는 년지 기준).
  - `get_gwimun(eight_char: dict) -> bool`: 귀문관살 여부 (일부 지지 조합 규칙).
  - 십이운성은 P2로 유보 가능(스펙에 "선택" 명시됨) — 최소 스텁 반환 + 미구현 명시.

- `app/prompts/saju_prompt_template.py`: 기존 SajuPromptContext/build_saju_prompt는
  일일 운세용으로 유지. 신규 파일 `app/prompts/saju_deep_reading_prompt.py`를 만들어
  DEEP READING 전용 시스템 프롬프트+사용자 프롬프트 빌더를 구현한다.
  - `DeepReadingContext` dataclass: eight_char, daewoon_list, sewoon_list(옵션),
    sinsal(옵션), mode(QUICK/STANDARD/DEEP), gender, birth_info 등.
  - `build_deep_reading_prompt(ctx) -> dict{system, user}`: 사용자 제공 전문 스펙의
    "역할과 범위/출력 첫 줄 고정문구/출력 모드/입력 계약/판독순서/고전 해석 원칙/
    작성 10단계/출력 공통 규칙"을 시스템 프롬프트로 이식. user 프롬프트는 계산된
    사주/대운/세운/신살 데이터를 구조화해 주입 (LLM이 재계산하지 않도록).

- `src/services/ai_interpreter.py`: 신규 함수 `interpret_saju_deep(ctx, mode) -> dict`
  추가. 기존 `_call_ai()` 공통 함수 재사용 (client, model=claude-sonnet-4-6,
  timeout 필요 시 DEEP은 max_tokens 상향, 예: QUICK 1500 / STANDARD 3000 / DEEP 6000).
  캐시는 DEEP READING 특성상(개인화 맥락 많음) 기본적으로 비활성 또는 매우 제한적으로.

- API 엔드포인트: `src/api/routes/saju.py`에 신규 엔드포인트 추가 권장:
  `POST /api/saju/deep-reading` — body: BirthInfo + mode(QUICK|STANDARD|DEEP 기본
  STANDARD) + 선택적 sewoon_years(향후 몇 년). 기존 rate_limiter 패턴 재사용
  (`@limiter.limit(...)`, 정밀 해석이므로 더 낮은 한도 권장 예: "5/minute").
  AI_OK 가드, 엔진 로드 실패 가드 기존 패턴 그대로 따를 것.

- 프론트엔드는 이번 스코프에서는 최소 API 계약만 맞추고 UI 연동은 별도 후속 작업으로
  남겨도 된다 (백엔드 우선, 존재하는 프론트 구조를 깨지 않는 선에서).

## 필수 검증 (완료 조건)

1. `python3 -m py_compile` 전체 새/수정 파일 PASS
2. 기존 테스트 전체 회귀 없음 (pytest -q, 기존 통과 건수 유지)
3. 신규 유닛 테스트 추가:
   - get_sewoon() 60갑자 순환 정확성 (예: 2024=갑진년 검증)
   - build_deep_reading_prompt()가 만세력 데이터 없이는 "판독 불가" 문구를 포함하는지
   - 모드별(QUICK/STANDARD/DEEP) 프롬프트 단계 포함 여부 차등 확인
   - 신살 하나만으로 사고/질병 단정하는 문구가 시스템 프롬프트에 없는지 (금지 규칙 검증)
4. 실제 AI 미호출 상태(ANTHROPIC_API_KEY 없음)에서도 API가 500 대신 graceful 처리
   (기존 `_AI_OK` 패턴 준수)
5. 출처 명시: 응답 JSON 또는 문서 주석에 "노이반 제공 전통 명리학 통합 해석 프롬프트
   (2026-08-10)" 출처를 남길 것 — 사용자가 "출처를 남겨주세요"라고 명시적으로 요청함.

## 하지 말아야 할 것

- 기존 일일 운세(daily-energy) 플로우를 손상시키지 않는다 (완전 별도 신규 엔드포인트).
- LLM에게 대운/세운/신살을 새로 "계산"하라고 요청하지 않는다 — 반드시 서버 계산값을
  구조화해 프롬프트에 주입.
- 사망/질병/사고 확정 표현이 출력되도록 유도하는 프롬프트 문구를 넣지 않는다.
- 신살 섹션이 격국/용신보다 먼저 나오거나 더 강조되는 순서로 설계하지 않는다
  (스펙 6단계 우선순위 원칙 — 본체 해석 후 보조 해석 순서 고정).
